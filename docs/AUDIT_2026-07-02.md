# Audit PandaMove — 2026-07-02

Audit global : sécurité, dépendances, fonctionnalités manquantes, limites/potentiel, et proposition
de structure `DESIGN.md` facilement modifiable pour une future refonte visuelle. Rapport d'analyse
uniquement — aucune modification de code applicative n'a été faite.

---

## 1. Sécurité

### Constats rassurants
- `allowBackup="false"` + `dataExtractionRules`/`fullBackupContent` excluent déjà `pandafit.db` (+ wal/shm) → pas de fuite de données via backup cloud/ADB.
- Toutes les `Activity`/`Service` sont `exported="false"` sauf `MainActivity` (normal, launcher).
- `FileProvider` correctement scoppé (`cache-path`, pas de `external-path` large), `grantUriPermissions` ciblé.
- Aucun secret/clé API en dur trouvé dans le code Kotlin (grep sur api_key/secret/token/password : rien de sensible).
- Pas de `google-services.json` présent dans l'arborescence actuelle malgré la mention dans CLAUDE.md/CONTEXT_COMPACT comme fichier sensible — soit il a été retiré, soit Firebase n'est pas (encore) intégré. **À vérifier** : si un jour ajouté, ne jamais committer sans `.gitignore`.
- Room utilisé sans SQL brut détecté dans le grep rapide → pas de surface d'injection SQL évidente (à confirmer par une revue DAO si des `@RawQuery` existent).

### Failles / points à durcir
1. **Pas de chiffrement de la base Room** (`pandafit.db` en clair sur le disque). Données de santé/activité (poids, séries, FC, GPS) accessibles si le téléphone est rooté/compromis. → Envisager SQLCipher ou Room + `androidx.security` (`EncryptedFile`) si le produit doit un jour stocker des données plus sensibles (ex. compte utilisateur, email).
2. **Aucune `network_security_config.xml`** trouvée → OSMDroid/Play Services location utilisent HTTPS par défaut sur API 31+, mais sans config explicite, un futur ajout réseau pourrait autoriser du cleartext par erreur. Ajouter un `network_security_config.xml` avec `cleartextTrafficPermitted="false"` explicite pour verrouiller ce comportement.
3. **Export/Import JSON (`DataExportManager`/`DataImportManager`)** : le fichier exporté (via `FileProvider`, cache) contient l'intégralité des données utilisateur en clair (séances, poids, GPS). Le partage via `Intent.createChooser` est correct côté Android, mais il n'y a pas de garde contre un import malveillant (fichier JSON forgé) — `ignoreUnknownKeys=true` protège du crash mais pas de données incohérentes injectées (ex. charges négatives, dates aberrantes). Ajouter une validation de bornes basique à l'import (valeurs numériques plausibles, dates non futures/absurdes).
4. **`versionCode`/`versionName` figés à 1 / "1.0.0"** dans `app/build.gradle.kts` — pas un risque sécurité en soi, mais empêche tout mécanisme de mise à jour forcée/détection de version obsolète si l'app est un jour distribuée.
5. **`isMinifyEnabled = true` + `isShrinkResources = true`** en release, bon réflexe — vérifier que `proguard-rules.pro` ne contient pas de `-dontobfuscate` ou de règles trop permissives qui annuleraient l'effet (fichier vide actuellement, à surveiller si des crashs de release apparaissent nécessitant des `-keep`).
6. **GPS foreground service** : bien scoppé (`foregroundServiceType="location"`), permissions correctes pour Android 14 (`FOREGROUND_SERVICE_LOCATION`). Rien à signaler, bonne pratique déjà en place.

## 2. Fonctionnalités restant à implémenter

D'après `docs/ai/CONTEXT_COMPACT.md` / `docs/ai/KNOWN_BUGS.md` / état déclaré dans `CLAUDE.md` :

- **Authentification / compte** : aucune trace de login, l'app est 100% locale (device-only). À décider si c'est voulu (positionnement offline-first) ou si un sync multi-appareil est sur la roadmap.
- **Sauvegarde cloud / sync** : `pandafit.db` explicitement exclu du backup Android → aucune sauvegarde automatique. Seul l'export JSON manuel protège contre la perte de données (changement de téléphone, désinstallation).
- **Images manquantes** (déjà notées dans CLAUDE.md) : timer, stats, profil — `docs/ai/HOME_BANNER_IMAGES.md`.
- **Historique cross-séance** : piège connu et archivé (`getHistoriqueForExercise` ne distingue pas bloc/séance) — filtrage plus fin à implémenter si le cas devient fréquent (échauffement vs superset du même exercice).
- **Version JSON d'export non actionnable** : le champ `version` est écrit mais jamais lu à l'import — un `when (export.version)` devra être implémenté dès qu'un changement sémantique de champ intervient (pas juste additif).
- **Notifications de rappel / planification proactive** : `WorkManager` est présent en dépendance mais aucun usage identifié dans l'exploration — potentiel non exploité (rappels de séance, relance motivationnelle).
- **Widget écran d'accueil** : aucune trace — potentiel classique pour une app fitness (séance du jour, streak).
- **Wear OS / montre connectée** : aucune intégration Health Connect / Wear détectée — les FC/GPS sont saisis manuellement ou via le téléphone seul.

## 3. Limites actuelles & potentiel

**Limites** :
- App mono-device, mono-utilisateur : perte du téléphone = perte de données sauf export manuel.
- Pas de chiffrement des données de santé stockées.
- Dépendance à OSMDroid (tuiles tierces) plutôt que Google Maps/Mapbox — moins fiable mais gratuit et sans clé API à gérer.
- `versionCode` figé — pas de mécanisme de mise à jour en place (cohérent avec un usage perso/hors store pour l'instant).
- Pas de tests d'intégration visibles au-delà des tests unitaires (`./gradlew test`) — pas de couverture UI (Compose testing) mentionnée.

**Potentiel** :
- Architecture modulaire déjà propre (MVVM+UDF, Hilt, Room versionné avec migrations incrémentales) → bonne base pour ajouter Health Connect, sync cloud (Firebase/Supabase), ou export vers Garmin/Strava sans réécrire l'existant.
- `ProgressionEngine` (moteur pur, testable) est un différenciateur produit réel (surcharge progressive avec inventaire matériel réel) — potentiel de mise en avant marketing si l'app est un jour publiée.
- Le design system (`core/designsystem`) centralisé (Color/Typography/Shape/Spacing) rend une refonte visuelle low-risk : changer les tokens suffit à repeindre toute l'app.

## 4. DESIGN.md — proposition de version "facilement modifiable"

Le `DESIGN.md` actuel mélange déjà bien règles + palette, mais la palette est noyée dans un tableau
Markdown au milieu du texte, pas isolée pour une itération rapide. Proposition : **extraire la
palette dans un bloc unique en tête de fichier**, façon "tokens à copier-coller", sans toucher aux
règles d'usage qui restent valables. Pas de changement de code Kotlin nécessaire pour cette étape —
uniquement réorganisation du Markdown (le mapping vers `Color.kt` reste à faire séparément lors de
la refonte réelle).

Proposition de bloc à insérer en tête de `DESIGN.md` (avant "Direction : Clean & Bold") :

```markdown
## 🎨 Palette rapide (modifier ici pour une refonte)

| Token                | Valeur    | Usage                          |
|----------------------|-----------|---------------------------------|
| PandaPurple          | `#7C5CBF` | Renforcement — primary          |
| PandaPurpleLight     | `#EDE8F7` | Renforcement — fond teinté      |
| PandaPurpleDark      | `#5A3D9A` | Renforcement — texte/bordure    |
| PandaGreen           | `#2E9E6B` | Running — primary               |
| PandaGreenLight      | `#E6F7F1` | Running — fond teinté           |
| PandaGreenDark       | `#1B6B46` | Running — texte/bordure         |
| PandaBlue            | `#1565C0` | Vélo — primary                  |
| PandaBlueLight       | `#E3F2FD` | Vélo — fond teinté              |
| PandaBlueDark        | `#0D47A1` | Vélo — texte/bordure            |
| PandaOrange          | `#E65100` | Calendrier — primary            |
| PandaOrangeLight     | `#FFF3E0` | Calendrier — fond teinté        |
| PandaOrangeDark      | `#BF360C` | Calendrier — texte/bordure      |

**Pour changer une couleur** : modifier la valeur ici ET dans `core/designsystem/.../theme/Color.kt`
(source de vérité runtime). Ce tableau est la référence de lecture rapide, `Color.kt` reste la
source exécutable.
```

Le reste du fichier (règles d'usage, typographie, composants, patterns d'écrans, checklist) est déjà
bien structuré et n'a pas besoin de changer pour l'instant — il sera à ajuster une fois la nouvelle
direction visuelle choisie (ex. si on change de palette ou qu'on introduit un dark mode réel, cf.
`ProfileViewModel.isDarkMode` déjà présent mais dont l'impact sur `Theme.kt` reste à vérifier).

**Fichiers concernés pour la future refonte visuelle** (repérés, non modifiés) :
- `core/designsystem/src/main/java/com/pandafit/designsystem/theme/Color.kt` — palette source
- `core/designsystem/src/main/java/com/pandafit/designsystem/theme/Theme.kt` — mapping extendedColors par sport
- `DESIGN.md` — doc à synchroniser après tout changement de `Color.kt`
